# 开源视觉 JEV 评测调研与 Vision-Jev 评测路线

更新日期：2026-09-29。

## 先说结论

开源视觉 JEV 项目通常同时展示两类结果，但两者不能混为一谈：

1. **正式测评**回答“模型判断得准不准、概率是否可信、遇到变化是否稳健”。结果应来自固定数据、固定协议和可复查的逐题记录。
2. **可视化推理速度**回答“模型在真实画面上看起来有多快”。它适合做演示，但只有在同步公布硬件、输入大小、预热、重复次数和计时范围后，才构成可比较的性能结果。

Vision-Jev 当前完成的是第一阶段内部 holdout 测评和逐题生成式延迟测量。由于训练与 holdout 来自相同的数据来源族，现有 85.55% 不是外部 zero-shot 结果。共享视觉前缀、原生概率头、外部未见基准和闭环测评仍待完成。

## 代表性项目做了什么

| 项目 | 正式测评 | 速度与可视化 | 值得借鉴的点 |
|---|---|---|---|
| [OmniJev](https://github.com/tinnel123666888/OmniJev) | 约 30 个视觉、视频、GUI、机器人、游戏和音频任务族；报告 macro/micro accuracy 与 ECE，并区分完全未见数据和同族保留集 | 同一图像一次请求 1/3/6/12 题；A800 上报告中位延迟和 12 题摊销延迟；另有带实测时钟的任务回放 | 明确区分聚合成绩、每任务成绩、校准和演示；同时公开不完整输入等限制 |
| [OneJev](https://github.com/OmniJev/OneJev) | OneJev test、DecisionBench hard、TypeSafe 对照和 MMStar 等面板，覆盖多种参数规模 | 1280×720 截图上测 1 题与 10 题；0.8B 在 H200 上为 31 ms/51 ms，即 10 题时约 5.1 ms/题 | 直接展示“读图一次、问题分支多次”的摊销价值；不同规模使用同一计时口径 |
| [PlayJev](https://github.com/OmniJev/PlayJev) | 10 个浏览器游戏，每个游戏 16 个未见 episode；同 seed 对比 random、teacher 和多个 DAgger 阶段，报告 teacher-normalized score；另测 MMBench/MMLU 保持能力 | 真实闭环回放叠加逐步动作概率；分析置信度接管和延迟一帧对游戏得分的影响 | 对行动模型，闭环得分比单步准确率更重要；“晚一步”的系统影响也应测量 |
| [Visual-Jev / SemIf](https://github.com/jiangxiluning/Visual-Jev) | 内部平衡集、WANLI、TypeSafe agreement、扰动与候选换序等；公开原始结果和校验值 | RTX 3090 上对比直接 typed logits 与自回归 JSON；还比较 fresh、串行前缀复用、并行后缀和 reranker，并提供交互回放/WebGPU 演示 | 将算法速度拆成生成、共享前缀和并行分支；同时检查加速是否改变 argmax |
| [OpenJev-Vision](https://github.com/IamBusy/OpenJev-Vision) | 合成图、Oxford-IIIT Pets、CLEVR-4 的三 seed 实验，独立校准，并公开组合泛化失败等负面结果 | 文本决策部分报告短/长输入 warm median；视觉部分更偏可复现实验而非实时演示 | 不只报最好结果，还报告失败边界、独立校准集和多 seed 波动 |
| [PixelJev](https://arxiv.org/abs/2609.29283) | Pets、CIFAR-10、EuroSAT、自然分布迁移、A-OKVQA、ScienceQA 等七组基准；比较冻结主干、adapter、few-shot、校准和置信区间 | 重点是视觉能力与样本效率，不以交互速度为主 | 外部迁移、few-shot 曲线和配对置信区间比单个总准确率更有解释力 |

这些结果不能直接横向排名：模型大小、硬件、输入分辨率、是否共享视觉前缀、数据是否见过以及任务定义都不同。表格用于提炼评测方法，不用于宣布某个项目“最快”或“最好”。

## Vision-Jev 的正式测评方案

### A. 发布回归集：已经具备

固定使用当前 5,771 题 group-safe holdout，报告：

- 总体与 Choice/Noul/Score 分项结果；
- 每来源结果，Score 同时报 exact、MAE 和相邻一级内准确率；
- JSON 合法率、失败样本和可复核的输出文件 SHA-256；
- 当前 117k SFT 完成后再发布内部与外部评测结果。

它用于版本回归，不称为外部 zero-shot。

### B. 外部未见评测：下一阶段

建议建立冻结的外部评测 manifest，并在任何针对性训练前完成首轮：

- **GUI/区域定位**：优先接入 [ScreenSpot v2/Pro 与 ScreenSuite](https://github.com/huggingface/screensuite) 中适合离线复现的点击或区域任务；
- **通用视觉决策**：选择未进入本项目 SFT 配方的公开 VLM 集，转换为候选式问题，并保留原始评分器；
- **候选结构鲁棒性**：候选换序、增删干扰项、K=2/8/16/32/64、近义候选和反事实成对测试；
- **视觉依赖性**：原图、遮挡关键区域、错配图像和无图四组配对比较；这里测的是图像依赖，不做没有任务意义的视频消融；
- **校准**：在原生决策头完成后报告 NLL、Brier、ECE、可靠性图和高置信错误。生成式 JSON 的单次答案不能冒充已校准概率。

“zero-shot”只表示该评测集及其任务定向样本未参与本项目后训练；基础模型不可审计的预训练重叠必须单独声明，不能保证绝对为零。

### C. 闭环评测：策略阶段再做

RLCD-inspired 校准后训练和 policy/value 分支完成后，再固定未见 seed 测成功率、累计回报、动作晚一帧的退化、置信度接管曲线和失败轨迹。SFT Preview 不应提前宣称闭环能力。

## Vision-Jev 的速度测评与可视化方案

### 正式速度基准

首个统一协议建议固定在单张 RTX 4090、BF16、同一 processor 和同一张 1280×720 截图：

- 问题数取 1、4、10、20，候选数与文本长度使用固定夹具；
- 冷启动单列，warm path 先预热，再至少重复 50 次；
- 报端到端 p50/p95、首题延迟、整请求延迟、每题摊销延迟、questions/s 和峰值显存；
- 计时包含图像预处理、视觉编码、问题分支和结果整理，不只截取 CUDA kernel；
- 对比当前自回归 JSON、未来原生决策头，以及是否共享视觉前缀；
- 每次保存环境、Git commit、夹具 SHA-256 和原始 JSON，不手抄图表数字。

当前 0.391 秒/题是逐题端到端平均值，可作为生成式基线，但不是共享图像多题吞吐结果。

### 可视化速度演示

从同一份原始 benchmark JSON 自动生成短视频或网页回放，画面只展示真实采集值：

- 左侧为输入图像和候选，右侧逐题出现答案；
- 顶部显示硬件、模型、问题数和输入分辨率；
- 时间轴区分图像预处理、视觉编码、首题完成和全部完成；
- 同时显示总延迟与摊销每题延迟，避免只挑最好的一次；
- 原生概率头完成后再加入候选概率条和校准信息；当前生成式 SFT 不伪造概率条。

演示应链接到同一 Git commit 下的正式结果文件。这样“看起来快”和“测出来快”来自同一份证据。

## 建议执行顺序

1. 保留现有 5,771 题结果作为 SFT 回归基线。
2. 先实现可重复的 1/4/10/20 问题正式速度脚本，再由其结果生成可视化回放。
3. 冻结一个无本项目后训练暴露的外部视觉评测集，先跑 base 与 SFT Preview。
4. 完成原生 Choice/Noul/Score 概率头后补校准、候选扰动和共享前缀对照。
5. 完成 RLCD-inspired 与 policy/value 后再发布闭环结果。
